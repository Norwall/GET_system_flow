# План Реализации Доработок Для `get_co2_model_upgrade_plan.md`

## 1. Цель документа

Этот документ переводит стратегический план из [get_co2_model_upgrade_plan.md](C:/Users/Prof_tmn/YandexDisk/GPN/Coding/mathCAD_to_PY/get_co2_model_upgrade_plan.md) в последовательный план реализации.

Задача плана реализации:
- разложить модернизацию по этапам;
- привязать этапы к текущим файлам проекта;
- определить, что именно меняется в коде;
- зафиксировать критерии готовности каждого этапа;
- сохранить работоспособность текущего интерфейса `CO2MathcadModel.run(...)` на переходный период.

## 2. Что есть сейчас

Текущая структура проекта по сути плоская:

- `get_co2_model.py` — вся физика, свойства, геометрия, решатель и результаты в одном файле
- `run_get_co2_demo-1.py` — сценарный запуск, sweep, отчеты и графики
- `get_co2_report-2.md`, `get_co2_sweep-1.csv`, `get_co2_sweep-1.png`, `get_co2_checks-1.json` — артефакты запусков
- `CO2.xmcd` — исходный Mathcad worksheet

Главное ограничение текущего состояния:
- файл `get_co2_model.py` одновременно выполняет роль property package, геометрической схемы, корреляционного слоя, steady-state solver и результата.

Поэтому реализацию улучшений надо начинать не с "добавить еще формулу", а с постепенного отделения физических подсистем.

## 3. Базовые принципы реализации

Во всех этапах соблюдать следующие правила:

- не ломать существующий внешний API без явной необходимости;
- все новые физические модели включать через переключаемые опции, а не заменять старое поведение сразу;
- сначала отделять архитектуру, потом усложнять физику;
- на каждом этапе сохранять регрессионное сравнение с текущей моделью;
- новое поведение делать opt-in, пока не завершена верификация.

## 4. Целевое состояние архитектуры

После нескольких этапов проект должен быть разложен хотя бы на такие модули:

- `co2_properties.py` — свойства CO2 и работа с таблицами/интерполяцией
- `co2_geometry.py` — описание геометрии контура и участков
- `two_phase_closures.py` — пустотность, скольжение, friction/pressure-drop correlations
- `co2_steady_solver.py` — steady-state решатель рабочего режима
- `co2_critical_solver.py` — поиск критических тепловых нагрузок
- `co2_results.py` — структура результата и сериализация
- `run_get_co2_demo-1.py` — демонстрационный runner, уже использующий новую архитектуру

Переходный слой:

- `get_co2_model.py` остается фасадом совместимости;
- внутри он импортирует новые модули и предоставляет прежний класс `CO2MathcadModel`.

## 16. Что делать в первой рабочей итерации

Первая итерация должна быть ограниченной и безопасной.

### Обязательные задачи первой итерации

- создать `tests/` и зафиксировать baseline
- вынести свойства в `co2_properties.py`
- вынести геометрию в `co2_geometry.py`
- вынести корреляции в `two_phase_closures.py`
- превратить `get_co2_model.py` в фасад совместимости
- ввести dataclass результата
- добавить физически понятные алиасы к неоднозначным выходам

### Что не делать в первой итерации

- не менять сразу математическую постановку
- не включать одновременно новый distributed solver
- не внедрять сразу критические режимы и динамику

### Почему так

Если смешать архитектурный рефакторинг и новую физику в одном шаге, станет невозможно понять, что именно изменило результат:
- новая формула
- новая интерполяция свойств
- новая структура кода
- или случайная регрессия

- проект готов к переходу к transient-модели без очередного переписывания архитектуры
